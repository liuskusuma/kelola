# Kelola

Aplikasi web statis (tanpa build step) untuk UMKM: kalkulator harga jual, kasir, laporan omzet/laba, plus login dan sinkronisasi cloud lewat Supabase. Nama sebelumnya: KalkuLaku, lalu UMKalc.

- Bahasa antarmuka, komentar kode, dan dokumen: Bahasa Indonesia yang sederhana. Pengguna adalah pemilik usaha kecil, kebanyakan memakai HP.
- Data bersifat local-first: semua perubahan lewat `store.put` / `store.remove` di `js/store.js`, lalu `scheduleSync()` di `js/app.js`. Jangan menulis ke Supabase langsung dari tampilan.
- Setiap catatan adalah satu baris di tabel `records` (`kind` = `produk`, `bahan`, `transaksi`, `pengeluaran`, atau `profil`). Konflik diselesaikan dengan "perubahan terbaru menang" berdasarkan `updated_at`.
- Desain: soft UI seperti aplikasi Bagi Rata (kartu menonjol, isian tertekan, judul Exo 2 miring), dominan putih dengan navy `#0a2a6e` dan kuning `#fecb10` dari logo (`icons/logo.png`, asli `icons/logo-asli.jpg`). Mode gelap memakai navy seperti tema Default Bagi Rata. Warna diatur lewat variabel CSS di `index.html`.
- Tampilan bawaan selalu terang (putih), walau HP memakai mode gelap; gelap hanya kalau dipilih di Akun (`data-tema` di `<html>`). Pengguna pernah mengeluh tampilan "dominan biru" karena HP-nya mode gelap.
- Semua teks antarmuka lewat `t('teks Indonesia')`; terjemahan Inggris ada di `js/bahasa.js`. Uji `tests/bahasa.test.js` gagal kalau ada teks tanpa terjemahan. Bahasa dan tema disimpan per perangkat (`kelola:pengaturan`), bukan di cloud. Bahasa bawaan English (permintaan pemilik); `tests/e2e.js` memasang Bahasa Indonesia lewat init script.
- Kategori produk: nama di `produk.data.kategori`, urutannya di `profil.data.kategori`; logika tanpa DOM di `js/kategori.js` (diuji `tests/kategori.test.js`). Produk tanpa kategori tampil di "Lainnya". HP staff menerimanya lewat `produk_kasir()`. Tombol "Atur kategori" sengaja di baris sendiri di bawah judul Daftar produk, bukan di samping "+ Tambah produk" (dulu disangka tombol tambah kategori).
- Varian dan tambahan (`js/varian.js`, tanpa DOM, diuji `tests/varian.test.js`): `produk.data.varian [{id, nama, banyak, pilihan: [{id, nama, harga}]}]`, `harga` = tambahan di atas harga jual. Produk bervarian membuka layar pilihan saat diketuk di kasir (pilihan paling atas tiap kelompok "pilih satu" terpilih otomatis; pemilik memilih cara ini supaya ukuran tidak salah); produk tanpa varian tetap sekali ketuk. Kunci baris keranjang (`ui.cart`) = id produk, atau produk + pilihan + catatan (`V.kunci`). Di penjualan disimpan sebagai teks `items[].varian` dan `items[].catatan`, dengan `items[].harga` sudah termasuk tambahan; modal/HPP tetap modal produk (tambahan belum punya modal sendiri). Laporan terlaris tetap per nama produk. HP staff menerima varian lewat `produk_kasir()`.
- Foto produk disimpan sebagai data URL JPEG kecil (maks 480 px) di `produk.data.foto`.
- Kalau mengubah file yang di-cache, naikkan `VERSION` di `sw.js` dan tambahkan file baru ke daftar `FILES`.
- Rumus HPP, saran harga, dan potongan stok ada di `js/hitung.js` (tanpa DOM). Modal produk resep/paket selalu dihitung ulang dari harga bahan saat ini; `data.modal` hanya catatan HPP saat produk terakhir disimpan, dipakai untuk peringatan harga bahan.
- Uji: `node --test` untuk logika sinkronisasi dan rumus, dan `tests/e2e.js` (Playwright) untuk alur di browser.
- Akun staff (`supabase/staff.sql`, `js/staff.js`): staff tidak bisa membaca `records` owner. Produk untuk kasir staff diambil lewat fungsi `produk_kasir()` (tanpa modal/resep). Penjualan staff masuk ke tabel `penjualan_staff`; HP owner mengambilnya (sekaligus menandai `diproses`) lalu mengubahnya jadi `transaksi` biasa lewat `KelolaPenjualan.olahPenjualanStaff` di `js/penjualan.js`. Jangan pernah mengirim modal, laba, resep, atau bahan ke HP staff.
- Mode kasir PIN hanya menyembunyikan tampilan di satu perangkat (`kunci` di `kelola:pengaturan`, PIN disimpan sebagai hash); bukan pengaman data.
- QRIS disimpan sebagai data URL di `profil.data.qris` (maks 900 px), hanya bisa diubah owner. HP staff menerimanya lewat `produk_kasir()`; setiap mengubah `supabase/staff.sql`, minta pemilik menjalankannya ulang.
- QRIS dengan nominal (`js/qris.js`, tanpa DOM, diuji `tests/qris.test.js`): kode QRIS toko dibaca dari gambar `profil.data.qris` di perangkat (`kodeQris()` di `js/app.js`, pustaka `vendor/jsqr-1.4.0.js`, hasil diingat per gambar), nominal disisipkan (tag 01 jadi `12`, tag 54, CRC tag 63 dihitung ulang), lalu QR baru digambar (`kanvasQr()`, pustaka `vendor/qrcode-generator-1.4.4.js`). Dipakai di "Tampilkan QRIS" kasir (total keranjang) dan gambar tagihan (sisa tagihan), juga di HP staff. Kalau gambar tidak terbaca atau dimatikan di Akun (`profil.data.qrisNominal === false`), semua kembali ke gambar QRIS biasa. Ini bukan QRIS dinamis resmi: tidak ada tanda lunas otomatis, dan pemilik sudah diberi tahu sebagian aplikasi pembeli mungkin menolak (ada tautan "Pakai QRIS tanpa nominal" di kasir). Pemilik menyetujui dua pustaka luar itu secara khusus; jangan menambah pustaka lain tanpa bertanya.
- Halaman Akun memakai bagian yang bisa dibuka-tutup (`lipat()` di `js/app.js`, status di `ui.lipat`). Uji e2e membuka semuanya dengan `bukaLipat()`.
- Cara bayar penjualan: `transaksi.data.metode` = `tunai` (bawaan, juga untuk data lama tanpa metode), `qris`, atau `nanti`. Penjualan `nanti` punya `pelanggan {nama, wa}`, `dibayar [{waktu, jumlah, metode}]`, dan `lunas`; sisa dihitung `KelolaPenjualan.sisaTagihan`. Omzet dan laba tetap dihitung saat penjualan, bukan saat dibayar.
- Logo dan warna usaha ada di `profil.data.logo` (maks 256 px), `palet`, dan `warna {utama, aksen}`. Logo juga tampil di atas struk penjualan (`strukGambar()`) dan gambar tagihan. Pinggiran putih/transparan logo dibuang saat tampil (`KelolaWarna.bersihkanTepi`, lewat `siapkanLogo()` di `js/app.js`; data logo tidak diubah) dan latar di belakang logo memakai warna tepi logo (di layar variabel CSS `--logo-latar` dan `logoTampil()`, di gambar `kotakLogo()`). Logo yang memang berlatar putih (bagian putih > 35%) dibiarkan dengan latar putih. Variabel CSS dibuat `js/warna.js` lalu dipasang di `<style id="temaUsaha">`. Tanpa `warna`, tampilan memakai navy dan kuning Kelola.
- Grafik Laporan: data dari `js/grafik.js` (tanpa DOM), digambar sebagai SVG oleh `viewGrafik()` di `js/app.js`. Warna batang `--grafik-1` (omzet) dan `--grafik-2` (laba), sudah dicek dengan validator palet: terang `#3159c8`/`#d99a00`, gelap `#6385ec`/`#b08200`; untuk warna usaha dibuat `js/warna.js`. Selalu sertakan legenda, tooltip, dan tabel.
- Layar awal (`viewGerbang()` di `js/app.js`): setiap aplikasi dibuka, pilih **Owner** (wajib kata sandi, termasuk kalau sesi Supabase masih ada) atau **Kasir / Staff** (langsung ke kasir; di HP tanpa data dan tanpa akun diminta masuk akun staff). Pilihan disimpan di sessionStorage `kelola:mode`, jadi muat ulang tidak bertanya lagi tapi menutup aplikasi bertanya lagi. Hash kata sandi terakhir (`kelola:sandi`) dipakai untuk masuk owner saat offline. "Pakai tanpa akun" hanya untuk HP yang belum pernah punya akun. Mode Kasir di HP owner hanya menyembunyikan tampilan, sama seperti mode PIN. Uji e2e melewati layar awal di `device()`.
- Laporan Excel: `js/excel.js` (tanpa DOM, diuji `tests/excel.test.js`) menulis .xlsx sendiri (zip tanpa kompresi). Setiap rumus selalu membawa hasilnya, supaya preview di HP/WhatsApp tetap menampilkan angka. Grafik di file berupa gambar PNG (`grafikPng()` di `js/app.js`), karena grafik bawaan Excel tidak tampil di preview HP. Belum ada kirim email otomatis (butuh layanan email + Edge Function).
- Ganti akun: daftar akun di localStorage `kelola:akun`. `store.claim()` menyimpan data akun yang ditinggalkan di `kelola:v1:akun:<userId>` dan memuat data akun tujuan. Keluar menghapus akun itu dari daftar. Staff dengan penjualan yang belum terkirim tidak bisa pindah akun.
- Face ID / sidik jari (`js/faceid.js`, passkey WebAuthn): pengganti mengetik kata sandi Owner di layar awal dan saat Ganti akun, per akun dan per perangkat (localStorage `kelola:faceid`: id kunci, plus `sesi` Supabase akun yang ditinggalkan kalau akun itu punya Face ID). Pindah dengan Face ID memperbarui sesi tersimpan lewat `fetch` langsung ke `/auth/v1/token` (bukan supabase-js, supaya akun aktif tidak ikut keluar kalau sesi itu sudah tidak berlaku), lalu `setSession`. Setelah owner masuk dengan kata sandi, kartu "Pakai Face ID untuk akun ini?" (`viewTawarFaceId()`) muncul di atas halaman; Face ID tidak diminta otomatis karena iPhone hanya mengizinkannya tepat setelah tombol disentuh. Tidak dipakai untuk PIN kasir atau akun staff (staff tidak pernah diminta kata sandi lagi). Keluar / Hapus dari HP ikut menghapus kuncinya. Uji e2e memakai authenticator tiruan Chromium (CDP `WebAuthn`).
- Penagihan (`js/tagihan.js`, tanpa DOM, diuji `tests/tagihan.test.js`): rekening di `profil.data.rekening [{id, bank, nomor, nama}]`, pengaturan di `profil.data.tagihan {jatuhTempo: 0|3|7|14|30 hari, ingatkan, mulai: 0|1|3}` (bawaan 7 hari, ingatkan, H-1). Jatuh tempo per tagihan di `transaksi.data.jatuhTempo` ('YYYY-MM-DD', boleh kosong untuk data lama); tagihan dari staff memakai jatuh tempo bawaan owner saat diambil. Semua diatur di Akun → "Cara bayar & tagihan" (lipat `qris`, juga berisi QRIS). Rekening tidak pernah dikirim ke HP staff.
- Setelah "Simpan & tagih" di kasir owner, layar Tagih (`bukaTagih`) langsung terbuka: gambar tagihan dari `gambarTagihan()` (logo + warna usaha, rekening, QRIS kalau ada) dan pesan WA pendek dengan nomor rekening dan nominal di baris sendiri, hanya angka (permintaan pemilik: satu pesan, tanpa pilihan gaya pesan). Warna tagihan selalu mengikuti "Logo & warna usaha", tanpa pilihan warna sendiri.
- Pengingat jatuh tempo: kartu `#pengingat` di Kasir dan Laporan, tanda merah di menu Laporan, "Nanti" menyembunyikan sampai besok (localStorage `kelola:pengingat`). Notifikasi HP: `supabase/notifikasi.sql` (tabel `push_langganan`, `push_kunci`, jadwal pg_cron 01.00 UTC) + Edge Function `supabase/functions/pengingat-tagihan/index.ts` (Web Push dengan Web Crypto, tanpa pustaka, kunci VAPID dibuat sendiri; diuji `tests/notifikasi.test.js` dengan Node). Fungsi itu ditulis tanpa tipe TypeScript supaya bisa diuji dengan Node; ubah juga logika `ringkas()` di sana kalau logika pengingat di `js/tagihan.js` berubah. Notifikasi disentuh membuka `./?buka=tagihan`.
- QRIS Midtrans (opsional per client, berbayar ±0,7% ditanggung client): `supabase/midtrans.sql` (tabel `midtrans_kunci`, `midtrans_bayar`, tanpa aturan RLS = hanya server) + Edge Function `supabase/functions/midtrans/index.ts` (tanpa tipe TypeScript, diuji `tests/midtrans.test.js`). Setiap client mendaftar Midtrans sendiri dan menempel Server Key di Akun → Cara bayar & tagihan (baris "QRIS Midtrans" di bawah saklar Nominal otomatis; pemilik tidak mau tiga pilihan terpisah). Server Key tidak pernah disimpan di HP, di `records`, atau dikirim ke staff; HP owner dan staff hanya memanggil fungsi itu (`panggilMidtrans()` di `js/app.js`). Sandbox otomatis dari awalan `SB-`. Kasir: QR dari Midtrans (Core API, `qris`), status ditanyakan tiap 3 detik, lunas → `simpanPenjualan()` otomatis (`transaksi.data.midtrans` = order id); dialog ditutup → pesanan dibatalkan; gagal → kembali ke QRIS biasa/nominal otomatis. Tagihan: link Snap di pesan WA (gambar tagihan tetap QRIS toko), pembayaran diambil saat owner sinkron (`prosesBayarMidtrans`, `P.olahBayarMidtrans`, `dibayar[].midtrans`). Tanpa webhook dan tanpa notifikasi HP untuk pembayaran ini.
- Versi aplikasi di `js/versi.js` (`window.KELOLA_VERSI`, format `1.<nomor PR tiga angka>`, misalnya PR #28 = `1.028`). Setiap PR baru wajib menaikkannya ke nomor PR itu (permintaan pemilik, untuk melacak versi). Tampil kecil di bagian bawah setiap halaman (`viewVersi()`: `#versiHalaman`, dan `#versiGerbang` di layar awal); pemilik tidak mau baris versi di Pengaturan.
